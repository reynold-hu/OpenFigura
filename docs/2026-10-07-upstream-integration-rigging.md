# Upstream source review and animation path — 2026-10-07

## Actual integration

Five requested repositories were cloned (not installed) into
`~/Desktop/Local/Opensource/`. Exact revisions and licence-file hashes:
`upstream-source-manifest.json`. No checkout setup scripts or model downloaders
were executed.

- **image-to-3dlab**: integrated pinned Apache-2.0 `photo_paint.py`, with attribution,
  optional numpy/Pillow dependencies, validated cameras/alpha/indices, explicit
  ROI/strength, protected material/geometry buffers and a separate candidate.
  CLI and MCP use the same engine. Real scifi case reproduced the experimental
  candidate hash, then inspected/rendered/exported it.
- **PartCrafter**: reviewed `scripts/inference_partcrafter.py`,
  `src/models/transformers/partcrafter_transformer.py` and its local/global attention
  design. The official runner hardcodes CUDA and substitutes a dummy degenerate
  mesh when a part is None. An OpenFigura adapter must refuse such a part, never
  record it as valid. Its optional VLM/style-transfer features can upload images;
  these are not appropriate defaults for OpenFigura's local contract. No model
  code or weights integrated this turn.
- **Hi3DGen**: reviewed `app.py` and `hi3dgen/pipelines/hi3dgen.py`: explicit
  normal estimation followed by normal-conditioned geometry. The app calls
  `.cuda()` and downloads several model families. Useful future geometry backend,
  not an installed Mac capability. An adapter must record normalization and
  normal-image evidence, and verify spconv/attention support first.
- **DetailGen3D**: reviewed `scripts/inference_detailgen3d.py`: normalizes input
  mesh by its bounding box and samples surface+normal points. `load_mesh()` calls
  `.cuda()` regardless of the later device selector; exported coordinates do not
  automatically restore the input frame. Any adapter must preserve inverse
  normalization and handle CPU/MPS as unavailable until actually ported/tested.
- **Hunyuan3D-2.1**: reviewed `hy3dpaint/textureGenPipeline.py`: view selection,
  normal/position conditioning, albedo/MR generation, enhancement, baking and
  inpainting. The reference is resized to 512; merely larger source input is not
  sufficient. Geometry and material stages should remain distinct; no wholesale
  copy of its CUDA pipeline or weights into the Mac package.

Generation now hashes any native raw PLY, base texture and staged SV camera/images
that actually exist. This keeps pre/postprocess evidence traceable without claiming
that those files are newly generated by OpenFigura itself.

## Fingers and animation

A static finger shape, a finger skeleton and good skinning are different problems.
Collapsed/merged fingers cannot be made anatomically correct merely by adding
bones. Hair, armour and clothing merged into a single noisy high-poly mesh also
need separate treatment before reliable deformation.

Recommended chain: preserve high-poly source → separate problematic hand/clothing
regions → repair hand mesh or fit a clean rigged hand template → retopology + bake
→ skeleton → skin weights → deformation tests → animation retargeting → real game
frame. A compatible clean hand template can reduce repeated finger generation, but
its dimensions, wrist seam and asset licence must be checked.

Open-source candidates (researched online, not installed or run this turn):

| Component | Role | Boundary |
|---|---|---|
| [Blender Rigify](https://docs.blender.org/manual/en/5.2/addons/rigify/index.html) | Human metarig/control rig, finger chains | Needs metarig fitting and skinning; not mesh repair |
| [UniRig](https://github.com/VAST-AI-Research/UniRig) | Skeleton prediction + skinning | MIT code; released weights/data scope differs from all paper results. CUDA/spconv stack; not verified on M5/16GB |
| [SkinTokens](https://github.com/VAST-AI-Research/SkinTokens) | Newer unified rigging research | Availability of compatible weights/runtime needs separate validation; no local compatibility claim |
| [Make-It-Animatable](https://github.com/jasongzy/Make-It-Animatable) | Humanoid bones, skinning and pose prediction | Optional neural backend; assess version/weights/licence and actual GPU memory |
| [Godot BoneMap + SkeletonProfileHumanoid](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html) | Reuse humanoid animation tracks | Requires correct rest pose, bone mapping and scale; does not create missing fingers |

Prefer Rigify for an inspectable Blender baseline, and validate UniRig or
Make-It-Animatable as alternative neural rigging backends on a suitable GPU.
No rig/skin/animation functionality has been implemented by this texture PR.
Do not repeat a paper's speed as measured latency on our machines.

Acceptance should include open hand / fist / finger spread, elbow and shoulder
bends, knee lift and squat. Check flipped joints, cloth penetration, detached hair,
weight leakage, collapse and original appearance. Bone counts or a valid GLB alone
are not animation acceptance. The present raised-hand scifi pose is a difficult
first rigging fixture; use a clean A/T-pose character for initial integration,
then return to it as a stretch test.

## Continuation: calibrated Rigify proof implemented

After this source-review phase, an experimental calibrated basic-human adapter
was added. It requires explicit bone coordinates; it does not infer a pose or
repair hand geometry. Native Bone Heat failed on the selected chibi (zero weighted
vertices); the capsule method is opt-in and labelled approximate. A decimated
candidate lost appearance and was abandoned; original high-poly geometry was kept
for the actual motion proof. Core/CLI/MCP, optional FK clips and pose-frame renders
now share the tool contract. See `calibrated-rigging.md` and the newer PROGRESS entry.
The four surveyed neural models remain undeployed.
